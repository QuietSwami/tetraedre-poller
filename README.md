# Tetraedre poller for FlintCORE (DMP)

The broader workspace includes `docs/FLINTCORE_TETRAEDRE.md` (analysis and rollout plan) and the 2026 `docs/DMP-Customer-Manual-en.pdf` (especially §§2.4, 7.2, 12.4 and 12.6). Those documents are not part of this standalone Git repository.

## Use

Create a **device profile** in the FlintCORE profile editor. This directory follows the [official `dmp-device-profiles` layout](https://github.com/orbiwise-sa/dmp-device-profiles): `profile.json` for profile metadata, separate `parametersSchema.json`, `stateSchema.json`, `services.json`, and one file per TypeScript module. When importing **this Git repository**, the only `.ts` files are `main.ts`, `poller.ts`, `sha256.ts` and `types.ts` at the root. Their DMP module names must be the corresponding bare names: `main`, `poller`, `sha256`, `types`. Test-only TypeScript declarations were removed from the repository tree because the Git importer treated the nested path as an invalid module name. If configuring manually, paste all four files into those named modules; `main` imports `poller`, which imports `sha256` and `types`. `profile.json` is *not* a complete `POST /rest/device-profiles` payload by itself. The checked-in `profile_uuid` identifies this profile; generate a different UUID if creating an independent copy. Use the editor's test functionality before saving or deploying. Set no connections.

Create one device for each **confirmed exact** TDS metering code and available media, with these device parameters:

- `url`: full HTTPS TDS endpoint (`.../io/web_service_json.php`), not the public demo server. The handler separately checks this shape in `poller.ts`; changing the parameter schema's `pattern` alone does not change that runtime check. If OCEau supplies a different URL shape, confirm the actual JSON API endpoint before adapting both checks.
- `username`, `dossierId`, and TDS `encryptedPassword` supplied by the TDS administrator. The last is a FlintCORE **secret** parameter; do not put values in source code or logs.
- `meteringCode`: the TDS metering code as given by the station owner; codes such as `AV_` and `VX_` have trailing underscores, which the handler accepts. For `AV_`, the public site displays measurement set ID 23, but verify that the authenticated API accepts `AV_` for your account.
- `media`: choose `7` for rain, `3` temperature, `6` river level, or `16` flow (if that station has it). DMP's profile schema requires **string enum values**; the handler converts the chosen string to a number for TDS. The **OCEAU-specific** output unit is derived automatically: `3 → °C`, `6 → m`, `7 → mm`, `16 → m3/s`. No `unit` device parameter is needed; a legacy `unit` parameter on an existing device is ignored. If the new derived unit differs from the old configured unit, the feed fingerprint changes and polling restarts at `startTimestamp` (potential replay). This labels data; it does not convert values. TDS's generic media 6/16 can have other units: confirm each actual series before onboarding it.
- `startTimestamp`: first desired UTC Unix timestamp **in seconds**. `windowSeconds` is optional; when omitted, the handler uses **3600 seconds**. If supplied, it must be an integer from 60 to 86400; adjust it to stay under 1000 readings per response.

Run `checkAccess`, then `pollNow`, and inspect the live log/upstream messages. The handler runs once per tick (5 minutes), processes one window, and catches up gradually. `checkAccess` checks folder-level export only; `get_values` with actual readings verifies access to that measurement set. The handler requests lowercase `format: 1` and accepts either the format-1 object or a **non-empty, fully validated** legacy format-0 array. It refuses empty format-0 arrays because they cannot distinguish no readings from denied access; this may stall polling across a fully empty window if TDS ignores lowercase `format`. Use a known populated test window to verify the feed and confirm whether the target server supports the format-1 wrapper before scaling. Never commit credentials or paste the full authenticated POST body into logs/tickets. **Timestamping:** each `result.upstream` message now includes a top-level Unix-**millisecond** `timestamp: t * 1000` to request source-time indexing. The nested object's `timestamp` (milliseconds) and `sourceTimestampUs` (microseconds) remain payload fields only. Verify the indexed message **Time** in FlintCORE after a pilot, since this top-level override comes from operator guidance rather than the manual. For bulk historical data, the separate JSONL import below still uses top-level Unix-**microseconds** and must not overlap the live poller without a deduplication plan.

**State Definition:** `stateSchema.json` declares four optional, non-secret fields visible in the device UI/API: `latestValue`, `latestTimestampMs` (source Unix milliseconds), `unit`, and `lastSuccessfulPollMs` (processing Unix milliseconds). After a fully validated `get_values` response, `result.state` keeps the latest reading (or preserves it for an authorized empty window) and records the poll time. If the runtime provides no initial state and the window is empty, there is no state to persist; the cursor still advances. FlintCORE's generated `DeviceState` TypeScript type treats declared fields as required even though this schema has no `required` list, so the handler narrows `info.state` before building `result.state`. Failed/ambiguous responses and `checkAccess` do not update state. This is a latest-reading snapshot, **not** a time series: the cursor and feed fingerprint remain in private `result.storage`. Historical JSONL imports do not themselves populate this live state. Deploy the state schema and event-handler change to the tenant profile before relying on it.

## Historical backfill (optional; do not overlap with live polling)

The 2026 FlintCORE manual (§7.2.3.2) documents a **separate** JSONL message import path with a top-level Unix-**microsecond** timestamp. From the surrounding workspace, `../scripts/fetch_tds_backfill.cjs` can fetch bounded TDS windows and call this converter automatically (see `../docs/FLINTCORE_TETRAEDRE.md`); it is not part of this standalone Git-imported profile. Alternatively, after registering the target device, save a single bounded, authorized TDS `get_values` **format-1 response or non-empty format-0 array** to a private JSON file and convert it offline (no TDS/FlintCORE credentials needed by the converter):

```sh
node backfill-jsonl.cjs \
  --device-uuid 'YOUR-REGISTERED-DEVICE-UUID' \
  --metering-code 'YOUR-EXACT-TDS-CODE' --media 7 \
  --t0 1709852400 --t1 1709938800 \
  tds-response.json > messages.jsonl
```

If conversion fails before validating readings, first check the **input** file's size (`wc -c < tds-response.json`) and ensure it contains complete JSON consisting of **only** `fetchResp.body`, not the live-log wrapper or a copied label such as `body: Object`. Keep the source and the `> messages.jsonl` destination as **different paths**: shell redirection truncates the destination before Node reads the source. Do not paste request bodies, headers or credentials into a JSON response file or shared logs. The converter never prints invalid JSON content in its error message.

Use the actual inclusive `t0`/`t1` of that TDS request; the converter derives the same OCEAU-specific unit from `media` and rejects denied format-1 objects, empty format-0 arrays, malformed, unsorted or out-of-window readings and verifies all rows before writing output. Upload the `.jsonl` via Devices → Import (`/app/import`) and check `/app/import-jobs` for failures. Start with a small pilot; the manual recommends exporting a real device/message first to confirm the import shape in your tenant. Don't upload both JSONL and live-poller data for the **same** period without an explicit deduplication strategy. Do not put TDS secrets in JSONL import records.

From this Git repository's root, run `node tests/typecheck.cjs` to check TypeScript against temporary sandbox globals (uses `npx` and TypeScript 5.9.3); these declarations are for local tests only, not a substitute for the tenant's live type definitions. Run behavior tests with `node --test main.test.cjs` (Node 22+). The local test loader simulates DMP's named-module imports; production uses the platform's module resolver. A successful local test does **not** mean the target server supports the requested format or FlintCORE's sandbox accepts this handler: validate in the target tenant before rollout.
